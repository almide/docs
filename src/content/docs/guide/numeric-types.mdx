Almide has two default numeric types and ten sized ones:

| | Types |
|---|---|
| Default | `Int` (64-bit signed), `Float` (64-bit IEEE 754) |
| Sized signed | `Int8`, `Int16`, `Int32`, `Int64` |
| Sized unsigned | `UInt8`, `UInt16`, `UInt32`, `UInt64` |
| Sized float | `Float32`, `Float64` |

`Int` and `Float` are what you want almost always. The sized types exist for
the places where width is part of the problem rather than an optimization:
binary formats, checksums, hardware and wire protocols, and interop with C or
WebAssembly.

Every sized-type module is auto-imported — `int8`, `uint32`, `float32` and the
rest are available with no `import`.

## Writing sized values

A sized value is written as an ordinary literal with a type annotation. There
is no literal suffix — `42i8` is a syntax error, since `i8` parses as an
identifier.

```almide
let a: Int8    = -128
let b: UInt8   = 255
let c: UInt32  = 0xdeadbeef
let d: UInt64  = 18446744073709551615
```

A literal that does not fit is a compile error, not a silent fold:

```
error[E024]: integer literal '200' is out of range for Int8
  hint: Int8 would silently fold to 0 here; its range is -128...127
```

## Conversion is always explicit

Almide has no implicit numeric widening. Mixing widths in one expression is an
error that tells you what to write:

```
error: operator '+' mixes sized numeric types Int32 and Int64 — explicit conversion required (e.g. `int32.from(x)`)
```

A conversion is named after the type it builds. Every numeric module (`int`,
`float`, `int8`…`int64`, `uint8`…`uint64`, `float32`, `float64`) has a `from`
that takes any numeric source — `Int`, `Float` or a sized type:

| From | To | Call |
|---|---|---|
| `Int` or `Float` | sized | `int8.from(n)`, `uint32.from(n)`, `float32.from(f)`, … |
| sized | `Int` | `int.from(x)` |
| sized | `Float` | `float.from(x)` |
| sized | sized | `int32.from(x)`, `uint8.from(x)`, `float32.from(x)`, … |

`T.from(x)` aborts when the value is not a `T` (a float is truncated toward
zero first). Each sized module also carries its own bounds (`min_value()`,
`max_value()`), arithmetic and bit operations, and `to_string`.

## Narrowing: abort, wrap, checked, or saturating

`T.from(x)` refuses a value that does not fit by aborting. When a narrowing
should not abort, three variants say what happens instead:

| Form | Returns | Behaviour |
|---|---|---|
| `int8.from(n)` | `Int8` | aborts outside `Int8`'s range |
| `int8.from_wrapping(n)` | `Int8` | keeps the low bits, two's complement (integer sources only) |
| `int8.from_checked(n)` | `Option[Int8]` | `none` unless `Int8` holds the value exactly |
| `int8.from_saturating(n)` | `Int8` | clamps to `Int8`'s range |

`from_checked` follows Swift's `Int(exactly:)`: it is `some` only when the
conversion is exact. From a float that means NaN, infinity, a fractional part
and out-of-range all give `none`.

`from_saturating` clamps to the nearest bound, and from a float NaN becomes `0`.

Float-to-integer conversion truncates toward zero and saturates at the type's
bounds; integer-to-float rounds to nearest, ties to even.

## Reading and writing binary

`bytes` reads and writes fixed-width values with the endianness in the name:

```almide
bytes.append_u32_le(b, value)          // grows `var b` by four bytes
bytes.put_f32_be(b, pos, x)            // overwrites four bytes at pos

bytes.get_u32_le(b, pos)               // Int?: none when out of range
bytes.get_f32_be(b, pos)               // Float?
```

The writers take a `var` binding (`mut` parameter); the readers return `none`
for a position past the end instead of aborting.

## Known rough edges

Two rough edges remain:

- **A sized-integer overflow the compiler can constant-fold breaks the native
  build** ([#901](https://github.com/almide/almide/issues/901)). `let a: Int8 =
  127` followed by `a + b` where `b` is `1` folds to `128` and emits an
  out-of-range `i8` literal. Going through a function call (so the fold cannot
  happen) wraps correctly to `-128` on both targets.
- **Mixing a sized type with plain `Int` is not caught.** `Int32 + Int64` is a
  clean error, but `Int32 + Int` type-checks and then fails in the native build
  or produces a wrong value on wasm ([#902](https://github.com/almide/almide/issues/902)).
  Convert explicitly.

Also note that `Int64` and `Float64` share a representation with `Int` and
`Float` but are distinct types, each with its own auto-imported module
(`int64`, `float64`); convert with `int.from(x)` / `int64.from(n)`.
